      2 ===================================
      3 
      4 :date: 2022-04-03
      5 :summary: solving sudoku puzzles with haskell
      6 
      7 My weekend project was to implement an algorithm for solving sudoku_ puzzles,
      8 and finally at 2am last night I had success.
      9 
     10 Solving sudoku puzzles is a common exercise in implementing recursive
     11 algorithms, much like the classic Fibonacci number algorithm, but unlike the
     12 latter it involves a very deeply nested decision space. An algorithm must
     13 traverse down an incorrect solution (exploring a given decision) in order to
     14 determine if it is incorrect. At that point, it must backtrack_ and test out a
     15 different decision. [1]_
     16 
     17 This decision space can be represented as a tree, where each decision is a node
     18 with 9 children. Each of the 9x9 cells represents one *level* of the decision
     19 tree. The full decision tree therefore has :code:`9^81` leaves [2]_. A
     20 backtracking algorithm scans this decision tree with brute force, checking if a
     21 given decision is valid, and if it isn't then it prunes that decision's
     22 subtree. If all 9 children of a node are invalid based on the puzzle's rules,
     23 then we know that node must be invalid too, and we can prune it and test a
     24 sibling subtree. Iterating through the tree this way, we eventually reach the
     25 last level with our complete puzzle.
     26 
     27 Sounds simple enough! Implementation may be another thing...
     28 
     29 At this point if you haven't tried to implement a solution but want to give it
     30 a go, I suggest waiting until you have before reading on.
     31

     38 This problem sounds like a perfect fit for Haskell, like everything, but
     39 specifically because Haskell's laziness allows us to 'pretend' to represent the
     40 entire tree without actually requiring it ever be evaluated. For anybody who is
     41 not familiar with Haskell, a more simple demonstration of this behaviour is
     42 that we can use infinite lists, such as :code:`posInts = [1..]`, and things
     43 work otherwise 'as you expect' because values are evaluated at access.
     44 
     45 Going back to the giant decision tree, when we are making our first decision --
     46 *"what value should we put in the first (empty) cell?"* -- we can simply map
     47 over all of the valid options with the same decision function recursively.
     48 Validity is determined by the known state of the puzzle (the initial values).
     49 
     50 To illustrate, here is semi-Pythonic pseudo-code:
     51 
     52 .. code-block:: python
     53 
     54     def attempt(state, cell) -> State | None:
     55         if is_beyond_last_cell(cell):
     56             # We need a way to check if the caller attempted to resolve the
     57             # very last cell.
     58             return state
     59 
     60         if not_empty(state[cell]):
     61             # This cell is filled, continue to find the next empty cell.
     62             return attempt(state, cell + 1)
     63 
     64         # Let's test values in this empty cell
     65         for candidate in valid_children(state, cell)
     66             result = attempt(candidate, cell + 1)
     67 
     68             if result is not None:
     69                 # We have found the answer!
     70                 return result
     71 
     72         return None
     73 
     74     attempt(initial_state, (1, 1))
     75 
     76 OK, so what's going on?
     77 
     78 1. First, we pass in the initial state -- our 9x9 grid with a small number of
     79    cells filled in -- and the coordinate for the first cell :code:`(1, 1)`.
     80 2. Inside :code:`attempt`, the first thing we do is check if we've gone beyond
     81    the last coordinate. If we have, the parent call has filled the grid, and we
     82    should just return the state.
     83 3. If that isn't the case, we check if the passed coordinate is completed. If
     84    it is, no problem, let's just continue to look at the next cell.
     85 4. If our cell of interest is empty, let's get its valid children. That is, if
     86    we stick in the numbers 1 though 9, which candidate states don't conflict
     87    with existing values? Then, recurse on :code:`attempt` with those candidate
     88    states.
     89 5. In the case where no children states are valid, we return :code:`None`, and
     90    the calling function continues its loop over sibling candidate states.
     91 
     92 If the initial state is valid, then one series of :code:`attempt` calls will
     93 make a path down to the final cell and we'll be left with the complete state,
     94 which is returned all the way up the call stack!
     95 
     96 The 'backtracking' here is implicitly encoded within the optional return type.
     97 If a decision is made in a given stack frame and we find out that all
     98 grandchildren are invalid, a :code:`None` is returned to us, and we continue
     99 with a new value in the current cell. If that was the last valid candidate at
    100 this level, this frame returns :code:`None` to backtrack to the parent.
    101 
    102 Haskell's lazy evaluation helps us keep the code concise because we can
    103 declaratively describe the traversal of our algorithm over the decision tree,
    104 and then only when we ask, for instance, for the first result, does evaluation
    105 proceed until we get it. If we asked for another result, traversal would need
    106 to continue to the very end before it could determine that there are no more
    107 possible results. This could be implemented in Python with generators, which
    108 similarly defer evaluation until an item is needed.
    109

    111 funny at the end when you realise the final implementation is much simpler than
    112 many of the ideas you come up with while figuring it out. If you have any other
    113 interesting problems I'd love to hear them so I can give them a go!

      9 After a few months of running a gitea_ instance on my website, the headache of
     10 putting up with it's sluggishness became too strong and I needed to replace it
     11 with something less heavy.
     12 
     13 Before I had set up gitea, I read briefly about cgit_ and, although it
     14 certainly looked attractive as a minimal, functional git server, gitea swayed
     15 me with the (long ongoing) discussion about federation between gitea instances.
     16 Federation between instances (and between gitea and gitlab instances, which has
     17 also been brought up) would be a real game-changer in the code-forge world. I
     18 don't deny that the practicality of github's interface has huge advantages;
     19 bringing that interface along with the graphical pull request and CI toolbox
     20 into the fediverse will definitely be a great thing to see. However this
     21 discussion has so far yielded very little, so despite my crossed fingers it is
     22 not currently a feature.
     23 
     24 Without federation in sight, I was using gitea as a single-user github
     25 substitute. The problem here is that these services are by design multi-user.
     26 For a single-user instance, pull requests and profile pages become redundant,
     27 all webpages and URLs concerning my repositories had to include my username,
     28 and very little of this can be compromised on. I appear to not be the only one
     29 expressing these woes - Jake Bauer has talked about his similar migration from
     30 gitea to cgit on paritybit.ca_.
     31 
     32 Moving to cgit was similar in experience to a well-made desktop program: a
     33 simple runtime config, a comprehensive man page, and a straight forward way to
     34 run it. After setting up the standard way (i.e. following the `arch wiki
     35 page`_) and giving the manual a once-over, it just needed some tweaks to the
     36 default CSS.
     37 
     38 The most striking improvement has the page-loading time, particularly after
     39 cgit has built up it's cache.
     40 
     41 On the index page, cgit can order repositories by age which is nice - however
     42 the dates all seemed to say the same thing. cgit seemed to be getting it's
     43 timestamps from the filesystem directly, so running this inside each repository
     44 was enough to change the timestamps on each file in a repository to that of the
     45 latest commit:
     46 
     47 .. code-block:: sh
     48 
     49     find . -type f -execdir touch -md "`git log -1 --pretty=format:"%ad" --date=iso`" {} \;
     50 
     51 I also wanted to set up write access, so that I can git push over HTTP as I do
     52 when pulling. cgit doesn't actually support this feature; this is with good
     53 reason, as git itself provides the means to do this using git-http-backend_.
     54 This can be used by an nginx server by adding a new location block as a sibling
     55 to the one proxying requests to cgit. In case this is of use to anyone else who
     56 uses cgit, here are my current read and write nginx location blocks:
     57 
     58 .. code-block:: sh
     59 
     60     # This block normally passes read requests to cgit
     61     location ~ ^/code(?:/(.*))?$ {
     62 
     63         # These if statements redirect write requests to the block below
     64         if ($arg_service = git-receive-pack) {
     65             rewrite /code/(.*) /git-write/$1 last;
     66         }
     67         if ($uri ~ ^/code/.*/git-receive-pack$) {
     68             rewrite /code/(.*) /git-write/$1 last;
     69         }
     70 
     71         include                 fastcgi_params;
     72         fastcgi_param           SCRIPT_FILENAME /usr/lib/cgit/cgit.cgi;
     73         fastcgi_split_path_info ^(/code/?)(.+)$;
     74         fastcgi_param           PATH_INFO       $fastcgi_path_info;
     75         fastcgi_param           QUERY_STRING    $args;
     76         fastcgi_param           HTTP_HOST       $server_name;
     77         fastcgi_pass            unix:/run/fcgiwrap.socket;
     78     }
     79 
     80     # This block passes authenticated write requests to git-http-backend
     81     location ~ /git-write/(.*) {
     82         internal;
     83         auth_basic_user_file    /etc/nginx/htaccess/git;
     84         fastcgi_pass            unix:/run/fcgiwrap.socket;
     85         include                 fastcgi_params;
     86         fastcgi_param           SCRIPT_FILENAME /usr/lib/git-core/git-http-backend;
     87         fastcgi_param           GIT_HTTP_EXPORT_ALL "";
     88         fastcgi_param           GIT_PROJECT_ROOT /var/git;
     89         fastcgi_param           PATH_INFO /$1;
     90         fastcgi_param           REMOTE_USER $remote_user;
     91         client_max_body_size 0;
     92     }
     93 
     94 With this setup, I can use :code:`git push` and it will let me update the
     95 remote repository after prompting for the username and password stored in
     96 :code:`/etc/nginx/htaccess/git`.
     97 
     98 So far I am loving cgit for what it is: a way to organise, view and display my
     99 projects without any unneeded features, and importantly without the need to go
    100 into the web interface to modify any repo information, as repo metadata is
    101 stored inside it's folder on the server.
    102 
    103 I'm surprised I don't see more people using cgit, though I expect that as time
    104 goes on and federation in code-forges becomes more of a thing that these more
    105 sophisticated platforms will become more popular. Until then, I'm very pleased
    106 with cgit.

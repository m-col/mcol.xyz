      1 Qtile: A Wayland Compositor
      2 ===========================
      3 
      4 :date: 2021-08-03
      5 :summary: Qtile: A Wayland Compositor
      6 
      7 What is this? Qtile? A Wayland compositor? Wut? You're reading right my dudes,
      8 now it is one. Since way before I joined the core Qtile dev team over a year
      9 ago there has been a vague drift in the codebase moving the X11-specific code
     10 into a :code:`backend` module with the aim of abstracting away the interface
     11 the WM makes with the X server. The idea was that other backends could be
     12 implemented and use the same higher-level management of windows, screens,
     13 groups (virtual desktops), the status bar, etc. Over the past few months I've
     14 been working on the first non-X11 backend: a Wayland compositor.
     15 
     16 This backend -- which was part of the latest release a few weeks ago (0.18.0)
     17 -- uses the Python CFFI wrapper around `wlroots
     18 <https://github.com/swaywm/wlroots>`_ created by flacjacket, `pywlroots
     19 <https://github.com/flacjacket/pywlroots>`_.  This in turn uses `pywayland
     20 <https://github.com/flacjacket/pywayland>`_ also written by Sean. Through
     21 pywlroots, Qtile gets access to the amazing work put in by the wlroots guys to
     22 make constructing a compositor straight forward and hassle-free.
     23 
     24 With the latest releases of the three projects above, launching Qtile as a
     25 Wayland compositor is as simple as running the following from a TTY:
     26 
     27 .. code-block:: python
     28 
     29    qtile start --backend wayland
     30 
     31 With it fired up, the first thing to notice is.... nothing!
     32

     41 So what are we looking at here? These two screenshots are my desktop running
     42 using the Wayland backend (top) and the X11 backend (bottom). Ignoring the
     43 difference in terminal (foot and xterm), everything else is the same. The same
     44 bar (Qtile's own bar), the same window borders, and (you'll have to take my
     45 word for it), the same keybinding and mouse behaviour.
     46 
     47 But why? Other than the totally valid reason of "it's awesome", I was getting
     48 sick of the visual glitches and imperfection that inevitably come with X, and
     49 this backend gives us pixel-perfect rendering [1]_. And testing them out one
     50 after the other it is certainly noticable. We also get nice things like easier
     51 to control clients (on the dev side *and* user side), `fewer buggy or slightly
     52 misunderstood interfaces <https://github.com/qtile/qtile/issues/2404>`_, but I
     53 don't need to supplement the many articles online about why Wayland is A Good
     54 Thing.
     55 
     56 Writing the backend was a great opportunity to refactor some of the code and
     57 really isolate and modularise the X11-specific parts as these are not used when
     58 ran for Wayland. It also helped shape the base classes required to create
     59 further backends. Based on their signatures, one can implement custom backends
     60 to handle whatever input-output setup one wants, be it a web-based compositor
     61 like `Greenfield <https://github.com/udevbe/greenfield>`_ or a VR desktop
     62 environment à la `Safespaces
     63 <https://arcan-fe.com/2018/03/29/safespaces-an-open-source-vr-desktop/>`_.
     64 
     65 I've got it running. What now?
     66 ------------------------------
     67 
     68 The first thing some people will notice when running a Wayland Qtile for the
     69 first time is that suddenly half of their programs no longer work. Many popular
     70 programs run on X only and alternatives need to be found. This can be as simple
     71 as replacing dmenu with `bemenu <https://github.com/Cloudef/bemenu>`_. Some
     72 fine people have collected links to alternatives for popular programs, so if
     73 this is what you want then check out `Are We Wayland Yet?
     74 <https://arewewaylandyet.com/>`_ and natpen on GitHub's `Awesome Wayland
     75 <https://github.com/natpen/awesome-wayland>`_ page.
     76 
     77 Some programs, such as Firefox or GTK and Qt-based programs, require
     78 environmental variables to be set for them to use their Wayland backend. For
     79 more info check out this page on the `Sway wiki
     80 <https://github.com/swaywm/sway/wiki/Running-programs-natively-under-wayland>`_.
     81 
     82 Many other compositors, such as Sway, support compatibility with X-only windows
     83 via the XWayland tool. This essentially serves as an X server that lets the
     84 compositor handle the pixel buffers of all the X clients so it can embed them
     85 within the Wayland desktop environment as regular windows. People who might
     86 want to use this in Qtile are unfortunately out of luck, as XWayland support is
     87 not implemented, and I am in favour of deferring its implementation
     88 indefinitely as it would introduce much more complexity to the code for what is
     89 ultimately a temporary workaround.
     90 
     91 Input configuration
     92 -------------------
     93 
     94 The X server reads config files from :code:`/etc/X11/xorg.conf.d` to use when
     95 configuring input devices managed via libinput. With many things, this becomes
     96 the responsibility of the Wayland compositor. Currently there is no common
     97 interface or configuration that can be shared between compositors, meaning each
     98 compositor has to manually deal with libinput configuration itself. I *have*
     99 implemented this in `this <https://github.com/qtile/qtile/pull/2548>`_ pull
    100 request, but I agree with the consensus that this feels wrong to have within
    101 Qtile. Sway does something similar; configuring libinput devices itself (with
    102 identical config options to X or that Qtile PR).
    103 
    104 It's a bad situation, but currently using the commit from that PR [2]_ is the
    105 only alternative to getting used to your input devices' default settings. My
    106 fingers and toes are crossed that a plug-and-play implementation comes onto the
    107 Wayland scene with a config that all compositors could use.
    108 
    109 But but... my dear drop shadows!
    110 --------------------------------
    111 
    112 In Wayland Qtile *is* the compositor so there can be no standalone compositing
    113 manager like under X. If you use `picom <https://github.com/yshui/picom>`_ then
    114 you need not worry about screen tearing at all, and transparency works native
    115 and out-of-the-box. Window drop shadows, however, are something that would need
    116 manual implementation within Qtile. In part I am hoping that somebody comes
    117 along and decides to hack away at a plugin for Qtile that will do this, because
    118 I do think drop shadows are out of the scope of Qtile proper. Alternatively if
    119 the wlroots people decide it's worth making this a trivial job for compositors
    120 then that would be even better. Either way, shadows are currently not possible.
    121 
    122 A note about the Systray
    123 ------------------------
    124 
    125 The crusty old Systray interface from X11 uses a very X-specific window
    126 embedding protocol and as a result can't be supported outside of X (and even
    127 with XWayland, it would only provide a systray interface for the X clients).
    128 
    129 Instead, the desktop-agnostic `Status Notifier Item
    130 <https://freedesktop.org/wiki/Specifications/StatusNotifierItem/>`_ dbus
    131 interface provides a protocol through which clients can specify icons and
    132 context menus for sticking in a system tray. This has roots in KDE's move to
    133 Wayland and has been adopted by many other Wayland servers as well as many
    134 client applications. Currently elParaguayo is `working on a widget
    135 <https://github.com/qtile/qtile/pull/2601>`_ that will provide this systray
    136 implementation, though this is a work in progress.

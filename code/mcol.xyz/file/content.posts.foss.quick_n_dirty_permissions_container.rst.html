      1 a quick and dirty permissions container
      2 =======================================
      3 
      4 
      5 :date: 2020-03-29
      6 :summary: A quick and dirty permissions container for a single program
      7 
      8 
      9 Although the vast majority of the software installed on my Linux daily driver
     10 is fully free and open source, and in general is trustworthy, over time I've
     11 had to make use of some programs that are closed source and created by entities
     12 who I wouldn't want to trust on my system.
     13 
     14 The quick and easy (lazy) solution I've opted for is to give these programs
     15 their own user and home directory and access to my normal user's X session.
     16 
     17 For example, we can create a user and home directory for steam (as root):
     18 
     19 .. code-block:: sh
     20 
     21    useradd --create-home steam
     22 
     23 We probably want our normal user to be able to launch the program with its user
     24 without needing to enter a password every time. To do this, we need to add a
     25 line equivalent to this to our sudoers rules:
     26 
     27 .. code-block:: sh
     28 
     29    mcol ALL=(steam) NOPASSWD: /usr/bin/steam
     30 
     31 If we were to launch it now, it wouldn't have access to the running X session
     32 owned by our normal user. We can use :code:`xhost` to give the new steam user
     33 access to the X session. This is best wrapped in a script that looks like:
     34 
     35 .. code-block:: sh
     36 
     37    #!/usr/bin/env bash
     38    xhost +SI:localuser:steam
     39    sudo --set-home -u steam /usr/bin/steam $@
     40 
     41 I call this script :code:`steam` and put it in a folder on my path inside my
     42 home folder. This way, I can just execute :code:`steam` as my normal user and
     43 the program runs as expected in my X session, but its permissions keep it
     44 restricted to its own home folder.
     45 
     46 This setup also lets us set firewall rules specific to the program, as nftables
     47 and iptables support the configuration of rules that match a user's UID. For
     48 example, if we wanted nftables to block connections from steam that weren't
     49 going through a VPN we could add this line to our outbound chain:
     50 
     51 .. code-block:: sh
     52 
     53    oifname $vpn_interface skuid steam accept
     54    oifname != $vpn_interface skuid steam reject
     55 
     56 Simple and great for those who wear tinfoil hats!

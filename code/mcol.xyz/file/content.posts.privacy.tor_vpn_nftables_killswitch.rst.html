      1 nftables as a tor and VPN killswitch
      2 ====================================
      3 
      4 :date: 2019-05-05
      5 :summary: nftables as a tor and VPN killswitch
      6 
      7 Truth be told, I never got the hang of iptables. nftables has a much nicer
      8 syntax and its improvements over iptables will lead to its dominance...
      9 eventually.
     10 
     11 This nftables configuration restricts outward network traffic to a locally
     12 running tor client, running as the user :code:`tor`, and a VPN interface, as two
     13 independent streams of traffic. This way I can allow any programs that aren't
     14 so tor friendly to use the VPN, and everything to go through tor directly.
     15 The whole file can be found `here <{static}/static/nftables.conf>`_.
     16 
     17 Usually the configuration file is at :code:`/etc/nftables.conf`.
     18 
     19 First, we need to flush any current rules:
     20 
     21 .. code-block:: Java
     22 
     23     flush ruleset
     24 
     25 Next, we create our first :code:`table`, which is of type :code:`inet`, and
     26 named :code:`restricted`. This type means is it applies to IPv4 and IPv6 both.
     27 
     28 .. code-block:: Java
     29 
     30     table inet restricted {
     31         chain inbound {
     32             type filter hook input priority 0;
     33 
     34 Within the table, we define our first :code:`chain` with the name
     35 :code:`input`.  We specify the chains behaviour on the first line in the chain.
     36 This chain is of type :code:`filter`, i.e. it will filter packets. We then give
     37 it the :code:`input` hook so it will act on incoming packets.
     38 
     39 Priorities can be set to order the chains relative to some internal Netfilter
     40 operations, see the `nftables wiki
     41 <https://wiki.nftables.org/wiki-nftables/index.php/Configuring_chains#Base_chain_priority>`_
     42 for more info. For a non-routing setup such as this one, priority of 0 works
     43 for everything, though it is important to note that packets will be tested
     44 against all chains using the relevant hook.
     45 
     46 Next is the first rule. It starts with a 'selector', which here is :code:`ct`
     47 for connection tracking, which uses packet metainformation to match packets.
     48 
     49 .. code-block:: Java
     50 
     51                 ct state {established, related} accept
     52 
     53 This rule matches packets by **state**, and matches those with state
     54 :code:`established` or :code:`related`.
     55 
     56 The rule ends with an action, in this case :code:`accept`. This rule will allow
     57 incoming packets from connections we've previously established, which means
     58 we've already allows them and they're safe. This accounts for most traffic so
     59 is best put first.
     60 
     61 Next, we accept packets with incoming interface name :code:`lo`, the loopback
     62 interface, which is required for many programs to work. Simple!
     63 
     64 .. code-block:: Java
     65 
     66                 iifname lo accept
     67 
     68 Next, we match packets by :code:`ip protocol`, of type :code:`icmp`. We match
     69 these more specifically by :code:`icmp type` with type :code:`echo-request`,
     70 and accept them. These are pings, which are fine to allow.
     71 
     72 .. code-block:: Java
     73 
     74                 ip protocol icmp icmp type echo-request accept
     75                 reject with icmp type port-unreachable
     76             }
     77 
     78 We end the chain by rejecting all other inputs with the 'port unreachable'
     79 message.
     80 
     81 We then create our output chain, another filter but this time with the
     82 :code:`output` hook. Again, we should accept all traffic on the loopback
     83 interface.
     84 
     85 .. code-block:: Java
     86 
     87     chain outbound {
     88         type filter hook output priority 0;
     89             oifname lo accept
     90 
     91 Now we start restricting our outward traffic. This rule matches connections
     92 being output from my wireless interface, :code:`wlan0`, so substitute the name
     93 of your main interface there. It accepts all traffic on this interface destined
     94 for the address listed, for example, the VPN server you're connecting to, and
     95 any local devices you wouldn't want to restrict.
     96 
     97 .. code-block:: Java
     98 
     99     oifname wlan0 ip daddr { 123.456.789.123, 192.168.1.3 } accept
    100     oifname wlan0 skuid tor accept
    101 
    102 On the second line, we allow outbound connections on the same interface where
    103 the UID of the originating socket (:code:`skuid`) is :code:`tor`. With a local
    104 tor client run as the user :code:`tor`, its connections will be accepted here.
    105 
    106 .. code-block:: Java
    107 
    108         oifname wg0 accept
    109         reject
    110     }
    111 
    112 It is definitely getting straightforward. Here we allow outbound connections on
    113 the :code:`wg0` interface, which is for my wireguard VPN. If your VPN might use
    114 a :code:`tun0` interface, in which case substitute that.
    115 
    116 Some commercial VPNs provide a proxy within their VPN tunnels, which can be
    117 used to further restrict what programs can can access the internet through the
    118 VPN. To do this, add :code:`ip daddr <proxy ip>` before the accept, and make
    119 any allowed programs use this proxy address for connections.
    120 
    121 We then close the chain rejecting all other traffic, blocking it from leaving
    122 your device.
    123 
    124 .. code-block:: Java
    125 
    126         chain forward {
    127 	    type filter hook forward priority 0; policy drop;
    128         }
    129     }
    130 
    131 Lastly, as we don't need to do any forwarding of packets we can create an empty
    132 chain with the hook :code:`forward`. This declaration also contains a default
    133 action, with :code:`policy drop`. We then close the table with :code:`}`.
    134 
    135 To enable this firewall, we can run this command with your config path substituted:
    136 
    137 .. code-block:: bash
    138 
    139     nft -f /etc/nftables/restricted.conf
    140 
    141 Most linux distros will package a systemd service file which can be edited and
    142 enabled to set up this firewall at boot.
    143 
    144 The only connections that can go out to the internet are connections on the VPN
    145 interface and any connections that the tor client makes, which can be accessed
    146 by programs using it as a proxy. This way we can ensure we know exactly what
    147 connections are allowed out and all connections that leave your machine are
    148 encrypted while in your ISP's hands.
    149 
    150 I highly recommend the nftables wiki especially the `quickstart guide
    151 <https://wiki.nftables.org/wiki-nftables/index.php/Quick_reference-nftables_in_10_minutes>`_
    152 once you're comfortable with the syntax.

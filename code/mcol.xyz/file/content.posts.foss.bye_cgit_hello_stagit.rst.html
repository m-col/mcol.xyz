      1 bye cgit, hello stagit
      2 ======================
      3 
      4 :date: 2020-10-04
      5 :summary: Not long ago I migrated my code hosting from a gitea instance to
      6           cgit, but now that's been replaced by stagit
      7 
      8 It was only around 2 months ago when I `replaced my gitea instance`_ with cgit_,
      9 but now I've replaced it with an even simpler alternative: stagit_.
     10 
     11 cgit, as per the name, is an application that uses `Common Gateway Interface`_
     12 (CGI) to serve dynamically generated web pages displaying information about the
     13 remote git repositories on your server. The CGI approach lets cgit check for
     14 updates to repositories when pages are requested in order to update these pages
     15 and its cache.
     16 
     17 stagit, on the other hand, is a command that generates static HTML pages from a
     18 repository just once when called. This reduces load on the server, as the pages
     19 can then be served directly without any dynamic page generation. The author has
     20 a blog post with some more information here_.
     21 
     22 As the scope of stagit is limited to generation of HTML pages, any requests on
     23 the server from git commands -- i.e. fetching or pushing -- must be handled by
     24 something else if they are to be supported. For this I am using
     25 git-http-backend_, to which nginx forwards requests that contain specific query
     26 strings.
     27 
     28 
     29 git hooks and regeneration
     30 --------------------------
     31 
     32 But how to update the pages? As stagit is a simple command invoked just to
     33 create new pages, it needs to called when git repositories are updated. For
     34 this, we can write a simple post-receive hook and link it into each of our
     35 repositories. Something like this, where our repos are in :code:`/var/git` and
     36 the output HTML files are saved into :code:`/var/www/code`:
     37 
     38 .. code-block:: sh
     39 
     40     # /var/git/<repo>/hooks/post-receive.d/update-stagit
     41     REPO=$(pwd)
     42     REPONAME=$(basename $REPO)
     43     cd /var/www/code/$REPONAME || cd /var/www/code/${REPONAME//.git} || exit 1
     44     stagit $REPO
     45     stagit-index /var/git/* > /var/www/code/index.html
     46 
     47 This will be executed at the end of every :code:`git push` that updates the
     48 repository, regenerating both the index page and the pages that pertain to the
     49 that repository.
     50 
     51 
     52 ordering the index page
     53 -----------------------
     54 
     55 You'll notice in the above snippet that there is a dedicated command for
     56 generating the index page, :code:`stagit-index`. The order of the repos on the
     57 index page is determined by the order of the arguments passed to this. To order
     58 these by most recent commit, I made a quick Python wrapper:
     59 
     60 .. code-block:: python
     61 
     62     # stagit-index.py
     63     import git
     64     import subprocess
     65     from pathlib import Path
     66 
     67     REPOS = []
     68     COMMAND = ["/usr/local/bin/stagit-index"]
     69 
     70     for path in Path("/var/git").glob('**/objects'):
     71         REPOS.append(
     72             (git.Repo(path.parent).head.commit.committed_date, path.parent)
     73         )
     74 
     75     COMMAND.extend(x for _, x in sorted(REPOS, key=lambda i: i[0], reverse=True))
     76     subprocess.call(COMMAND)
     77 
     78 Then all I need to do is run this little script and the index page will display
     79 the repositories with the most recent updates first.
     80 
     81 
     82 hacking the source
     83 ------------------
     84 
     85 As the source code is neat and simple, it's very easy to make changes to
     86 customise the behaviour. For example, I wanted every page to use the same
     87 global stylesheet, rather than using a hard-coded path beside the given page. I
     88 also removed the "Owner" column from the index page. Changes such as these --
     89 essentially modifying the HTML template used -- are unfortunately impossible
     90 with cgit, although some larger forges such as gitea do have full HTML template
     91 systems.
     92 
     93 Indeed, reading the source code it is clear that it would not be too difficult
     94 to create a similar program that does exactly what you want. Though, if a
     95 similar program took advantage of an HTML templating engine, then hacks such as
     96 these may no longer be necessary. That would be more flexible... but where's
     97 the fun in that?
